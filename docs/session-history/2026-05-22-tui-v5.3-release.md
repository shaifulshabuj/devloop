## Key decisions and why

### Spec corrections caught during preflight

The redesign brief in `devloop-tui-redesign 3/` had 7 factual errors. All
were corrected during implementation and the table is in `CHANGELOG.md`
under `[5.3.0]`. Highlights:

| Brief said… | Reality (shipped) |
|---|---|
| Permit queue: filename = command | UUID-named JSON: `.json` filename is UUID; command in body |
| Gate timeout in `worker.state` | No such file — status is in `.devloop/sessions/<TASK-ID>/status` |
| Provider health: `DEVLOOP_*_OVERRIDE` | Real names: `HEALTH_MAIN_*` / `HEALTH_WORKER_*` |
| Detect escalation by stdout scrape | Built NDJSON `phase.escalate` event instead |
| TUI tails `.devloop/pipeline.log` | Authoritative file is `.devloop/events.ndjson` |

### Wording: "quiet" not "stuck"

A no-output running phase is called **"quiet"** in the UI, never "stuck".
Reasoning: a long refactor can legitimately run > 10 min and "stuck"
implies failure, which causes users to press `Z resume` and corrupt a
healthy run. "Stuck" is reserved for the genuinely-blocked gate-timeout
case where action is actually required.

### Single shared viewport in Focus Mode

LOG / SPEC / DIFF / PERMIT tabs all share one `bubbles/viewport`,
swapping content on tab change. Simpler state, smaller memory footprint,
no risk of state diverging across tabs.

### Palette dispatches via chat, not its own subprocess driver

When a palette action fires, the router switches to ViewChat and
forwards the `uimsg.PaletteRun{Command,Arg}` message. Chat's existing
`dispatchShell` handles the subprocess. **No new subprocess pattern.**
Output streams into the same scrollback as manual slash commands.

### Cross-package messages live in `internal/uimsg/`

`app` already imports `views`. Putting cross-cutting messages
(`OpenFocus`, `CloseFocus`, `PaletteRun`) in either of those packages
would create an import cycle. `uimsg` is a leaf package — depends on
nothing, depended on by everything.

### One worktree per phase, not per issue (per plan)

Within a phase, multiple issues touch overlapping files (`app.go`,
`dashboard.go`). Separate worktrees per issue would cause constant
rebases. Instead: small PR-sized commits straight to `main`, squashed,
with each commit closing one issue.
